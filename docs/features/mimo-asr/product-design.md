# Type4Me MiMo-V2.5-ASR 产品设计

> 分支：`feat/211-mimo-asr`
> 文档类型：产品设计
> 文档状态：设计中
> 关联 Issue：#211
> 设计日期：2026-08-24
> 目标版本：Type4Me 2.x
> 官方文档：https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/audio/Speech-Recognition

## 1. 背景

Issue #211 希望 Type4Me 支持小米 MiMo-V2.5-ASR。Type4Me 当前已经具备多 ASR Provider 架构，同时既支持真正的实时流式 ASR，也支持在录音结束后提交完整音频的 Batch ASR。

MiMo-V2.5-ASR 的接口形态更接近后者：客户端需要先提供完整的 WAV 或 MP3 音频，并将音频编码为 Base64 后放入一次 Chat Completions 请求。`stream=true` 只表示识别文本以 SSE 增量返回，并不意味着录音期间可以持续上传 PCM 音频。

因此，本功能的核心产品判断是：

**MiMo-V2.5-ASR 在 Type4Me 中应被定义为“非实时语音识别 Provider”，而不是实时流式 ASR。**

## 2. 产品目标

### 2.1 核心目标

1. 为中国用户增加一个低门槛的 BYOK 云端 ASR 选择；
2. 支持 MiMo-V2.5-ASR 的中文、英文和自动语种检测；
3. 保持与 Type4Me 现有 Batch ASR 一致的录音与输出体验；
4. 在模型返回 SSE 增量时，尽快展示识别文本，减少“松手后完全无反馈”的等待感；
5. 明确向用户说明该 Provider 不支持边说边出字；
6. 对 10 MB Base64 音频限制提供可理解、可恢复的错误体验；
7. 不引入新的账号体系、代理服务或订阅依赖。

### 2.2 成功标准

1. 用户可在“语音识别引擎”中选择“小米 MiMo（非实时）”；
2. 用户配置有效 API Key 后即可正常完成录音转写；
3. 松开快捷键后提交完整录音，并在服务端返回文本时逐步更新浮动栏；
4. 最终识别文本能进入 Type4Me 现有 Direct、LLM 处理和文本注入流程；
5. 中文、英文及自动检测均能正确映射到 MiMo API；
6. 超出服务端限制时不会发送必然失败的请求，而是直接给出明确错误；
7. API Key 只存储于 macOS Keychain；
8. 中英文界面文案完整覆盖新增设置和错误提示。

## 3. 非目标

第一版不包含：

- 录音期间实时上传 PCM 音频；
- 将 MiMo 标记为“流式 ASR”；
- 自定义模型名称；
- 自定义 MiMo Base URL；
- MP3 本地编码；
- 音频自动分片与多请求拼接；
- 热词、Boosting Table 或自定义词表能力；
- 手动关闭 MiMo 自动标点；
- 服务端代理、Type4Me Cloud 转发或统一计费；
- 将 MiMo 加入首版“推荐 Provider”列表；
- 为 MiMo 单独设计录音交互模式。

## 4. Provider 定位

### 4.1 用户可见名称

中文：`小米 MiMo（非实时）`

英文：`Xiaomi MiMo (Batch)`

名称中明确标记“非实时 / Batch”，避免用户把 SSE 文本返回误解为 Deepgram、豆包、Soniox 等真正的实时音频流。

### 4.2 Provider 分类

MiMo 放入 ASR Provider 的“中国”分类，与火山引擎、阿里云百炼、百度等 Provider 同组。

第一版不加入“推荐”分组。是否推荐应基于后续真实识别效果、延迟、稳定性和成本评测，而不是仅基于厂商宣传。

### 4.3 适用场景

适合：

- 中文为主的短到中等长度语音输入；
- 中英混合输入；
- 希望尝试 MiMo 官方方言能力的用户；
- 可接受“松开后识别”的用户；
- 希望自行持有 API Key 的 BYOK 用户。

不适合：

- 强依赖边说边出字的输入场景；
- 单次超长录音；
- 强依赖热词参数的专业词汇场景；
- 离线使用。

## 5. 核心交互

### 5.1 录音阶段

用户按住或切换快捷键开始录音后：

- Type4Me 正常采集并缓存 PCM；
- 浮动栏显示通用的“录音中…”状态；
- 不向 MiMo 发起网络请求；
- 不展示伪实时识别结果。

### 5.2 松开快捷键

录音结束后：

1. Type4Me 将 PCM 封装为 WAV；
2. 检查 Base64 编码后的音频大小是否会超过 10 MB；
3. 构造 MiMo Chat Completions 请求；
4. 使用 SSE 模式提交；
5. 收到文本增量后立即更新浮动栏；
6. 收到完成事件后冻结最终文本；
7. 进入现有 Direct / LLM 后处理 / 注入流程。

### 5.3 用户感知

用户体验应清楚表现为：

`录音中 → 正在识别 → 识别文本逐步出现 → 完成`

而不是伪装成：

`录音中同时实时出字`

## 6. 设置设计

### 6.1 凭证字段

第一版只提供：

| 字段 | 类型 | 默认值 | 是否必填 |
|---|---|---|---|
| API Key | Secure | 空 | 是 |
| 识别语言 | Picker | `auto` | 否 |

语言选项：

- `auto`：自动检测；
- `zh`：中文；
- `en`：英文。

模型固定为 `mimo-v2.5-asr`，不显示模型选择器。

### 6.2 设置说明

Provider 下方显示：

中文：`松开快捷键后提交完整录音；MiMo 的流式模式仅表示识别文本通过 SSE 返回，不支持录音期间实时上传。`

英文：`The complete recording is submitted after you release the hotkey. MiMo streaming only streams transcript text over SSE; it does not accept live audio chunks while recording.`

### 6.3 指引链接

设置页提供：

- 官方接入文档；
- API Key 获取入口。

链接应使用小米官方域名，不使用第三方教程。

## 7. 音频限制

### 7.1 官方限制

MiMo 当前仅支持 WAV 和 MP3，Base64 编码后的音频字符串上限为 10 MB。

Type4Me 第一版统一使用 WAV，不增加 MP3 编码链路。

### 7.2 Type4Me 侧预检查

在发请求前计算实际 Data URL 长度。若超过限制：

- 不发起网络请求；
- 浮动栏进入失败状态；
- 不注入不完整文本；
- 提示用户缩短本次录音。

建议文案：

中文：`录音过长，超过 MiMo 单次音频大小限制，请缩短后重试。`

英文：`The recording exceeds MiMo's per-request audio limit. Please record a shorter segment and try again.`

### 7.3 为什么第一版不自动分片

自动分片会引入：

- 句子被切断；
- 多请求之间缺少上下文；
- 标点和重复内容拼接；
- 重叠窗口与去重策略；
- 错误恢复和部分成功状态；
- 多请求费用与速率限制放大。

对于语音输入法的典型短录音场景，这些复杂度第一版不值得引入。

## 8. 语言与方言

MiMo 官方接口允许 `auto`、`zh`、`en` 三种语言参数，并宣称模型支持中英双语及粤语、吴语、闽南语、四川话等中国方言。

产品层面只暴露 API 明确支持的三个参数，不单独增加“粤语”“四川话”等 Picker 项，因为官方 API 没有为这些方言提供独立 language code。

方言能力作为模型自身自动识别能力，不在 Type4Me UI 中承诺特定准确率。

## 9. 热词与标点

### 9.1 热词

当前 MiMo ASR API 没有提供可映射到 Type4Me `ASRRequestOptions.hotwords` 的公开参数。

因此第一版：

- 不发送 HotwordStorage 内容；
- 不报错；
- 不在 MiMo 设置中显示“支持热词”的暗示。

### 9.2 标点

MiMo 官方说明会自动生成标点，当前 API 没有公开关闭标点的参数。

因此 `enablePunc` 对 MiMo 不生效，Type4Me 不尝试模拟关闭。

## 10. 错误体验

至少覆盖：

| 场景 | 用户提示 |
|---|---|
| API Key 为空 | 配置无效 |
| HTTP 401 | API Key 无效或已禁用 |
| HTTP 403 | 当前 API Key 无权访问 MiMo ASR |
| HTTP 429 | 请求过于频繁，请稍后重试 |
| 音频为空/过短 | 没有录到有效音频 |
| Base64 超 10 MB | 录音过长，请缩短后重试 |
| SSE 解析失败 | MiMo 返回了无法解析的识别结果 |
| 服务端主动错误 | 优先展示服务端错误信息 |
| 网络超时 | 连接超时，请重试 |

所有文案必须提供中英文版本。

## 11. “测试连接”产品决策

Type4Me 当前部分 Batch Provider 的“测试连接”只执行 `connect()` 再 `disconnect()`；如果真实 HTTP 请求只在 `endAudio()` 时发生，这个测试并不能验证 API Key。

MiMo 第一版不能复制这种误导行为。

产品要求：

- 如果没有一个不会产生真实转写费用的官方鉴权检查接口，则 MiMo 的“测试连接”应明确执行一个最小有效请求；或
- 将 Batch Provider 的测试能力抽象为专门的 credential validation；
- 在技术实现完成前，不允许仅凭本地 Config 初始化成功就显示“连接成功”。

## 12. 隐私与安全

- API Key 使用现有 Keychain 存储；
- 非安全字段仅保存语言代码；
- 音频只在用户主动使用 MiMo Provider 时发送给小米服务；
- Type4Me 不额外持久化 Base64 请求体；
- Debug 日志不得输出 API Key、完整 Base64 音频或完整 Authorization Header；
- 错误日志最多记录状态码、错误类型和有界服务端错误文本。

## 13. 可观测性

建议继续使用现有 ASR 日志体系记录：

- PCM 字节数；
- WAV 字节数；
- Base64/Data URL 字节数；
- 请求开始时间；
- 首个 SSE 文本增量时间；
- 最终完成时间；
- 最终文本字符数；
- HTTP 状态码；
- 错误类别。

不得记录完整音频或凭证。

## 14. 验收场景

### 14.1 基础功能

1. 配置有效 API Key；
2. 选择 `auto`；
3. 录制一段中文；
4. 松开快捷键；
5. 浮动栏从“录音中”切换到识别结果；
6. 最终文本正确注入。

### 14.2 英文

选择 `en`，输入英文，确认最终文本和标点正常。

### 14.3 中英混合

使用 `auto`，输入中英混合内容，确认服务可正常完成识别。

### 14.4 Direct 与 LLM 模式

分别验证：

- Direct 直接注入；
- 快速模式；
- Intelli Sense；
- 翻译；
- 自定义 Prompt 模式。

MiMo 只替换 ASR 层，不改变后续 ProcessingMode 语义。

### 14.5 大小限制

构造超过 MiMo 上限的录音，确认：

- 请求未发送；
- 用户收到明确错误；
- 没有部分文本被错误注入。

### 14.6 错误凭证

使用无效 API Key，确认设置页测试和真实识别均不会显示假成功。

## 15. 发布策略

第一版作为普通“其他 / 中国云端”Provider 发布，不标记推荐。

发布后重点观察：

- 首字延迟；
- 松手到最终结果延迟；
- 401/403/429 比例；
- 超过大小限制的真实发生频率；
- 中文、中英混输和方言用户反馈；
- 用户是否误解“流式”含义。

如果超长录音限制成为高频问题，再单独设计音频分片方案。

## 16. 后续可能演进

- 支持官方未来推出的真正实时音频流 API；
- 如果官方增加热词参数，映射到 Type4Me HotwordStorage；
- 如果官方增加更多明确语言代码，再扩展语言 Picker；
- 为所有 Batch Provider 统一改造“测试连接”；
- 基于真实测评决定是否进入“推荐”Provider；
- 在有充分需求时设计安全的长音频分片识别。
